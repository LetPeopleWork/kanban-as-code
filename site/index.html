Kanban as Code v0.1 draft. It will change as we build.

Your Kanban system as plain files in git

Keep your work items and their full history as plain files, in an open format that any tool can read. With Kanban practices built in, and enforced.

Works with git: use any provider, or keep it local.

Kanban is not optional

Any tool lets you set up a board without WIP limits, policies or an SLE. Here, that workflow is not valid. Every team that uses the standard has to decide how it works.

  • WIP control. Every workflow says how the team limits work in progress.
  • Service level expectation. Every workflow has one.
  • Explicit policies. Every state has its policy written down.
  • Flow data. Every move is recorded, so cycle time, WIP, work item age and throughput come from the files.

Built on the Kanban Guide.

Two kinds of file

workflow.md: how your team works

One file per workflow. It holds your states, how you limit WIP, your policies and your service level expectation.

cards/*.md: one file per work item

Each card holds where it is now and how it got there, so a tool needs nothing but the file.

Why a standard

  • No lock-in. Your work and its history outlive any one tool or provider.
  • Your choice of view. Many tools can read the same files. Pick one, use several, or build your own.
  • Agents and people on one board. The work sits next to the code, where agents already work.
  • Versions and audit trail from git. Who moved what, and when, without extra tooling.

The standard defines how the work is stored. It does not tell you how to show it. A board, a chart or a forecast can come from a tool, an agent skill or a script.

Use cases

Developer with an agent

The agent picks a card, does the work, and moves the card in the same commit.

Single team

One workflow file and the cards. Flow metrics come from the history.

Several teams

Each team has its own workflow, folder or repo. One tool reads them all.

Portfolio

Parent and child cards across more than two levels, in the same format.

Tool maker

Read the files and show a board. Write them back and keep the history.

Metrics and forecasts

Read the transitions, then show flow metrics and Monte Carlo forecasts.

Product owner or manager

See where the work is in a viewer, without touching git.

Agent

Reads the workflow to learn the states and policies, then moves cards.

What we aim for

  • One simple format for work items and their history.
  • Kanban practices built in: WIP control, policies, an SLE.
  • From one team to many teams, many repos and several levels.
  • Any tool can read and write it: UIs, agents, scripts, metrics tools.

Questions

Why not GitHub Issues with a coding agent?

Your cards stay files in your repo, with their history in each file. It works with git, so you can use any provider or keep it local, and change tools without losing your data.

Who owns this?

LetPeopleWork wrote it. We plan to make it more public later and open it up to more people. The standard is under CC BY 4.0, so anyone can use it.

Is it stable?

Not yet. It is a first draft, and it will change as we build the first tools on it.
